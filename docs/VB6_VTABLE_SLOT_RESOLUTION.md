# VB6 对象表 / vtable 槽号解析（路线 2 全过程与结论）

> 目标：把 `call [eax+0xNNN]` 里的槽号一次性翻成方法名，解决立柱函数 17 个输入通道的语义。
> ⚠️ **本文第一～七节的结论「静态解析做不到」已被第十节推翻**（我只测了控件实例，没测 Form 类）。
> ⚠️ **第十节也被第十一节推翻了**（`.data` 里那些块零 xref，不是 vtable）。
> **最终结论看第十一节**：这个 VB6 EXE 的方法地址**不在静态数据里**，静态无解。

---

## 一、为什么静态解析不可能：vtable 是运行时造出来的

在 V31 里取一个 TextBox 的控件对象（`GetWindowLong(hwnd, 0)`），读它的"vtable"：

```
hwnd=0xE0A12  obj=0x0C744408
  [obj] = 0x0C752E48        ← 堆地址，不在 0x400000–0x229F000 镜像范围
     +0x000 = 0x048A0BD4
     +0x004 = 0x00000020
     +0x008 = 0x7FFFFFFE
     +0x0A0 = 0x00000006
     +0x314 = 0x00000000
```

⇒ **VB6 的控件 vtable 是每个实例在堆上现造的**，不在 EXE 里。
所以「从镜像里找 vtable → 读槽 → 得方法名」这条路**从根上不成立**。

这也解释了为什么镜像里能找到 34 个"连续代码指针块"却对不上——它们不是 vtable（见第三节）。

## 三、确实找到了方法名表，但没有引用者

在 `.text` 段里扫「连续 DWORD 都指向合法标识符」，得到 6 组**确定是方法名表**的块：

| 地址 | 项数 | 内容 |
|---|---|---|
| `0x4D3274` | 5 | `otherjy spide prnt virus qmd` |
| `0x4D32F8` | 10 | `QIU2 QIU1 QIU3 QIU5 QIU7 QIUm1 QIUm2 qiu_zq_4_4a qiu_zq_4_4B` |
| `0x4D3ED4` | 3 | `QIUM QIUNAODU QIUFAI` |
| `0x4D4358` | 3 | `QIUFAI QIUFAI1 QIUFAI2` |
| **`0x4D43CC`** | **18** | **`jisuan_0 Xcdm jisuan_1 Xcdm1 jisuan_2 Xcdm2 XCDM_AUTO_ XCDM_AUTO_1 XCDM_AUTO_2 jisuan1_0 jisuan1_1 jisuan1_2 jisuan2_0 Xcdm_hc_ jisuan2_1 Xcdm_HC_1 jisuan2_2 Xcdm_HC_2`** |
| `0x4D4978` | 5 | 同第一组 |

数组前后都是零填充（固定槽位），但**反查引用全部为 0**：

```
0x4D43CC  VA 引用 0 处；RVA(0xD43CC) 引用 0 处
0x4D32F8  VA 引用 0 处；RVA 引用 0 处
```

⇒ VB6 不用绝对指针指向方法名表。没有 ObjectInfo 就无法把「数组顺序」与「vtable 槽号」对上。

另外 `0x4D6C34` 一带是**控件名表**（`Text17 Text16 … Command10 … Frame18`），
`0x52Exxx` 一带是**事件绑定表**（`Command8` + GBK 中文事件名）。
三者（控件名 / 方法名 / 事件）都有，但缺把它们串起来的那层结构。

## 四、34 个"函数指针块"是什么（已排除）

在非代码段扫「连续 ≥30 个指向代码段的 DWORD」，得到 34 块，全在 `0x220E914–0x221B908`：

| 块地址 | 指针数 | 块地址 | 指针数 |
|---|---|---|---|
| `0x220E914` | 71 | `0x2219064`… | 53 |
| `0x22125C8` | 44 | `0x221A068` | 82 |
| `0x2214364` | 40 | `0x221A8B4` | 80 |
| `0x2214B08` | 49 | `0x221B0F8` | 67 |
| `0x22152D0` | 67 | `0x221B908` | 85 |

读它们的 `+0x0A0 / +0x314 / +0x334`：

```
0x022125C8  +A0=0x4579DC  +314=0x732F708C  +334=0x732F70CC
0x02214364  +A0=0x0       +314=0x732F70AC  +334=0x732F70EC
0x022180BC  +A0=0x731F2F45 +314=0x732F70CC +334=0x732F710C
```

`0x732Fxxxx` 当时被当成 msvbvm60（假定基址 `0x731F0000`），**这个假定后来被证伪**：
实测 V31 进程里 `0x731F0000` 属于 **comctl32.DLL**、`0x732F70CC` 属于 **WININET.dll**，
而 msvbvm60.dll 的真实基址是 **0x734D0000**。所以按 RVA `0x1070CC` 去 msvbvm60 导出表查名字**无效**——
脱壳镜像是运行时 dump，里面的绝对地址只在**那一刻**成立，换进程/换启动就对不上（ASLR）。
**要看指向哪个模块，必须用模块相对偏移，并在同一进程内换算。**

查 msvbvm60 的导出表（1911 个函数 / 635 个名字，注意下面的 RVA 换算因 ASLR 前提已失效）：

```
RVA 0x1070CC → 无导出名
最近的导出：0x106B5F __vbaStr2Vec（差 1389 字节）
            0x106B1E __vbaR8ForNextCheck
            0x106AE0 __vbaVarDiv
```

⇒ 这些槽指向运行时的**非导出内部函数**，静态拿不到名字。
且这 34 块里没有一个包含立柱函数入口 `0x1D442DA`，也不是 Form 的 vtable（原因见第一节）。

## 六、还剩的唯一可行路

**运行时按窗体逐个 dump**：

1. 取窗体对象指针（`GetWindowLong(hwnd,0)` 对窗体是 0，需另找：`SetProp` 链、
   `ThunderRT6FormDC` 的 `cbWndExtra` 更大偏移、或 `WM_GETOBJECT/OBJID_NATIVEOM`）；
2. 读运行时 vtable（堆地址），把 `+0x0A0`、`+0x314`、`+0x334` 等槽的函数地址取出来；
3. 这些函数地址若落在 msvbvm60 → 查导出名/内部偏移；若落在 EXE → **直接反汇编**，
   函数体里会有 `push <控件索引>` 或 `mov eax,[ecx+off]`，据此定位是哪个控件。

第 3 步是关键：**只要槽指向 EXE 内代码，就能反汇编出它读哪个字段**。
所以下一步应当先解决"第 1 步——窗体对象指针"。

## 八、第二轮：继续挖到的三个硬事实（含一个纠错）

### 8.1 ★ 纠错：msvbvm60 基址不是 0x731F0000

实测 V31 进程模块表（Toolhelp）：

```
mqjssv31.exe   base=0x00400000  size=0x018C5000
msvbvm60.dll   base=0x734D0000  size=0x0015D000
comctl32.DLL   base=0x731F0000        ← 之前误当成 msvbvm60
WININET.dll    base=0x73210000        ← 0x732F70CC 实际属于它
```

⇒ 第七节"按 RVA 0x1070CC 去 msvbvm60 导出表查名字"**整个前提是错的**，该结论作废。

### 8.2 ★ ASLR 陷阱：dump 里的绝对地址只在那一次成立

`unpacked_runtime.exe` 是**运行时 dump**，里面的指针值是 dump 那一刻的地址。
换一次启动、换一个进程，模块基址就变了 ⇒ 跨进程/跨启动比较绝对地址**全部无效**。
判"指向哪个模块"必须：**同进程取模块基址 → 算模块相对偏移 → 再解释**。

### 8.3 V31 的 PE 布局（ASPack，与 V35 不同）

```
文件 2.8 MB
  .text    VA=0x00401000  vsize=0x01890000(25.7MB)  rawsize=0x0002B7400(2.8MB)   ← 壳内压着，运行时展开
  .data    VA=0x01C91000  vsize=0x00018000          rawsize=0x00000200
  .rsrc / .aspack / .adata
```

⇒ **V31 在内存里是展开的 25.7MB 代码**，但磁盘上只有 2.8MB。
`0x48F490`、`0x493298`、`0x4B8C78` 都落在 `.text`（解压后）里——
**但 VB6 把常量、字符串、对象表也塞在 .text**，所以"在 .text 里"不等于"是代码"。

### 8.4 卡点

对 `0x48F490` 直接反汇编得到 `adc al, 0x3a` ——不是函数入口。
把它归类为 vtable 槽或数据都**无法证实**，因为：
- V31 未脱壳，手里没有"地址 → 函数边界"的可靠图（V35 是靠 IDA 建函数才有的）；
- 用 `msvbvm60 范围 + .text 范围` 当判据扫堆，得到 45,841 个候选块（噪音淹没信号），
  说明"连续代码指针"这个特征在 25MB 展开代码面前区分度太低。

## 九、结论与下一步（明确的）

**结论**：槽号 → 控件名，在「V31 未脱壳」的前提下做不出来。
不是方法不对，是缺一张"V31 的地址→函数"地图。

**下一步（按性价比排序）**：

1. **把 V31 也脱壳**（复用 V35 已有的 aidbg 流程 → `unpacked_v31.exe`），
   然后照 V35 那套五步法分析。到手后：
   - 用 `v35_varflow.py` 建 V31 的函数索引；
   - 在 V31 里跑 `预演`，断点/内存法定位 Form 对象；
   - 读 vtable 槽 → 指向的函数 → 反汇编 → 得到控件索引。
2. 或者**横向绕开**：不去解槽号，改为**行为对齐**——
   在 V31 界面上逐个改输入框，看哪个改动让 `A`/`B` 两个量跟着变（A/B 的数值可从
   公式反解出唯一解，属于"程序状态直读 + 输入对照"，不是反推内部取值）。
   这条路不需要脱壳 V31，代价是要设计一组能区分 A、B 的输入实验。

## 十、★ 更正：Form/类的 vtable 是静态的（第一～七节的结论作废）

### 10.1 我之前错在哪

第一节我测的是 **TextBox 控件实例**的 `GetWindowLong(hwnd,0)` → `[obj]` 是堆地址，
据此断言"VB6 vtable 运行时构造、静态不可能"。**这个推断越界了**：
控件实例可以有自己的运行时壳，但 **Form/类模块的 vtable 是编译期生成的静态表**。

### 10.2 实测：V31 的 .data 里有 37 张 vtable

扫 V31 内存镜像（`v31mem_clean/v31_mem_00401000.bin`）的 `.data` 段（`0x1C91000–0x1CA9000`），
找「连续 ≥8 个指向代码段的指针」，得到 **37 张表**，槽数 8–144：

| vtable | 槽数 | `+0` | `+0xA0` | `+0x314` | `+0x334` |
|---|---|---|---|---|---|
| `0x1C9C8A0` | 91 | `0x49C025` | `0x49BDE9` | `0x735D6F14` | `0x735D6F54` |
| `0x1CA0184` | **144** | `0x4C7068` | `0x4C7270` | `0x735D6D6C` | `0x735D6DAC` |
| `0x1C9F934` | 83 | `0x4B5428` | `0x4B5247` | `0x735D6F54` | `0x735D6F94` |
| `0x1C9E0A8` | 80 | `0x48BF01` | `0x48BFC4` | `0x735D6F6C` | `0x735D6FAC` |
| `0x1C928D0` | 72 | `0x41511C` | `0x1C933B0` | 0 | 0 |

- `+0` / `+0xA0` 落在 **V31 代码段**（`0x401000–0x1CD0000`）且**各不相同**；
- `+0x314` / `+0x334` 落在 **msvbvm60**（基址 `0x734D0000`，即 `+0x106xxx`）——
  和 V35 镜像里同名槽的偏移**完全一致**，反证 V35/V31 同源。

⇒ **37 张表 ↔ 35 个窗体**，基本一一对应。

### 10.3 vtable 槽 → 真实函数（三层跳转已打通）

V35 镜像里同样有 vtable（`.data` 段 `0x220D000` 起，365 个候选，≥25 槽）。槽的值是 `e9 xx xx xx xx`（`jmp rel32`）：

```
vtable+0xA0 = 0x4579DC   →  jmp 0x21F103F  →  push ebp; mov ebp,esp; sub esp,0xc; push SEH…（真函数）
vtable+0xA0 = 0x4960DF   →  jmp 0x2161201  → 同上
vtable+0xA0 = 0x4C8413   →  jmp 0x20AB144  → 同上
```

⇒ **跟一层跳板就能拿到真实的 VB6 Sub**，可以直接反汇编、可以下拉变量流分析。
**这就是之前缺的那张"地址 → 函数"地图。**

### 10.4 还差一步：立柱函数不在 vtable 里

对 V35 的 365 个 vtable、每个前 200 槽做「跟跳板后是否等于 `0x1D442DA`」的匹配：**命中 0**。

说明立柱计算是 **Private Sub**（或挂在控件事件上），不进 Form 的 vtable。
VB6 的控件事件走**事件表**（V31 里 `0x52Exxx` 一带：`Command8` + GBK 中文事件名 + 函数指针的组合）。
⇒ 下一步应当解析**事件表**，而不是继续在 vtable 里找。

### 10.5 修正后的可行路线

1. **用 .data 的 vtable 直接查槽号**：`+0x0A0` → 跟跳板 → 反汇编那个 Sub →
   看它读 `this` 的哪个字段 / 调用哪个子对象。**不需要先认出是哪张表**，
   因为同一槽号在不同 vtable 上指向不同函数，逐个看就能区分。
2. **认表**：37 张表按槽数排序，与 35 个窗体的控件数/方法数对照；
   或解析事件表把「控件 → 事件 → 函数」串起来。
3. 有了 1、2，`call [eax+0x0A0]` 的语义就能钉死。

## 十一、★ 用 IDA MCP 复核：第十节也错了

打开已有 IDB（`local-data/recon/unpack/unpacked_runtime.exe.i64`，263MB，无需重新分析），用 IDAPython 复核：

### 11.1 四条否定性证据

| 检查 | 结果 |
|---|---|
| `sub_1D442DA` 是否被调用 | **xrefs = 0**。<br>全段搜值 `0x1D442DA`（4 字节）：**0 处** |
| 计算书字符串 `0x4DA2A2`「单元框抗弯强度计算值」 | `idautils.XrefsTo` → **0**；全段搜指针值 → **0** |
| 第十节那批「vtable」的 xrefs | **全部 0** |
| 那批块的前 0x20 字节 | 全是 `0x732F798C, 0x732F7994, 0x732F799C…` 间隔 **8** 递增——是 msvbvm60 的**运行时表项**，不是虚表头 |

⇒ **`.data` 里「连续代码指针块」不等于 vtable**。第十节的 37 张表 / 365 个候选，
按形状判据选出来的，实际上没有代码引用它们。

### 11.2 Hex-Rays 是能用的（这部分收获保留）

槽 `0x4579DC → jmp 0x21F103F`，`add_func` 后反编译成功，伪代码形如：

```c
sub_419AC0();                                  // VB 栈检查
v3 = *v2; (*(void(**)(void))(v3 + 4))();        // AddRef
...
(*(void(**)(void))(v4 + 1276))();               // 调 this 的 vtable+1276 方法
savedregs = sub_419CBE();                       // __vbaObjSet
...
(*(int(**)(void))(v6 + 84))();                  // 取属性
```

⇒ **"地址 → 函数 → 伪代码"这条链是通的**，缺的只是"槽号 → 哪个函数"的静态映射。

### 11.3 最终结论

这个 VB6 EXE **所有 Sub 的方法地址都不在静态数据里**：
没有 vtable 引用、没有字符串 xref、没有 `push offset`。
VB6 把窗体方法做成**运行时构造的分派表**（`__vbaNew` 时按 ObjectInfo 生成），
所以静态分析到"地址"就断链了。

**这不是工具问题**（IDA 已经确认了四次否定证据），是 VB6 的编译方式决定的。

### 11.4 因此只剩运行时

要拿「槽号 → 控件/方法」，只能在**运行中的 V31** 上做：

1. 取窗体对象（`GetWindowLong(hwnd,0)` 对窗体是 0，需另找）；
2. 读它的**运行时**方法表（堆地址）；
3. 把 `+0x0A0` 等槽的函数地址取出来，与**同进程**的 `MQJSSV31.EXE` 基址（`0x400000`）算偏移；
4. 拿偏移去 V31 的内存镜像（`v31mem_clean/…00401000.bin`）反汇编 → 得到函数体。

**这一步缺的只是"窗体对象指针怎么取"**。已知：
- 控件的对象指针在 `GetWindowLong(hwnd, 0)`（实测 TextBox → `0x0C744408`）；
- 窗体的 `cbWndExtra = 0`，所以 Windows 侧不存。

可行取法（未试）：
- 在堆里搜「值 = 窗体 hwnd」的 DWORD，附近若有指向 msvbvm60 的指针，就是 Form 对象；
- 或 `WM_GETOBJECT + OBJID_NATIVEOM` 取 IDispatch。
